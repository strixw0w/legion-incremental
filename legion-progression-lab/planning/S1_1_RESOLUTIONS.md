# S1.1 — resolutions for the correction pass

**Version 1.0, 2026-11-13. Status: proposed candidate rules, awaiting owner acceptance.**

> **Pointer (the proposals below are unchanged):** the owner resolved S1.1-R01 … R15 after the independent S1.1 review. See `S1_1_OWNER_RESOLUTIONS.md` v1.0 (R10 subject to the estimator correction in `S1_1_ACCEPTANCE_ADDENDUM.md`).

The owner's S1 review (§2–§7) set the direction for each correction. Where an exact rule was still needed to implement it, the rule is written here with its consequence, in line with "do not silently invent gameplay rules". Owner resolutions of S1-R01 … R17 are in `S1_OWNER_RESOLUTIONS.md`.

Specs updated:

- `gates.md` v1.1;

| ID | Topic (owner §) | Rule (candidate) | Consequence if changed |
|---|---|---|---|
| S1.1-R01 | Respecting a repeated-death stop (§3) | A zone is **blocked** for a realistic policy while the hero's level is at most the level at which auto-farm last stopped there for repeated deaths (`deathStop`, shown to the player). A blocked zone is never turned on for auto-farm and never chosen as a farming target. After **one level-up** the block lifts, and returning is a deliberate retry. | A longer block (for example two levels) means fewer retry cycles and fewer deaths, but slower return to the newest zone. |
| S1.1-R02 | Recovery steps (§3) | All corrected realistic policies apply, in order: (1) **rest** below 30% HP between fights; (2) in a blocked zone, **retreat** one adjacent step at a time toward the highest-order accessible, non-blocked zone below it whose displayed estimate is not "unreachable"; (3) if none exists, turn auto-farm off and **`Report(NO_SAFE_ZONE)`**, then stay idle. POL-FIXED-n reports `FIXED_ZONE_BLOCKED` instead of moving. | POL-STAY now rests, which it never did in S1. That is a policy change, reported separately in S1.1-E01/E04. A different rest threshold changes resting time and deaths. |
| S1.1-R03 | Combining policy triggers (§4) | All decision requests at one `(t, pass)` form one decision. The observation carries every trigger, without repeats, in a fixed order (`TRIGGER_ORDER`). New triggers: `hero-died`, `auto-farm-stopped`, `boss-cleared`, `boss-failed`. Decisions at other timestamps are separate and never suppressed. | Decision counts change; realistic policies' commands do not (they never read the trigger). ORC-BRUTE now re-plans at gate completions. |
| S1.1-R04 | Policy cascades (§4) | More than **8** policy decisions at one timestamp is an engine error (`EVENT_CASCADE_LIMIT`). | A policy that loops is reported as a failed run, never as an infinite loop or a silently dropped decision. |
| S1.1-R05 | Manual retry (§3) | The engine never re-enables auto-farm. An accepted `SetAutoFarm(on)` after a stop is a **manual retry**: it clears the stop reason; the recorded deaths stay in the window, so one more death inside it stops auto-farm again. `Engage` is always allowed. The S1 controls retry at once; realistic policies only after S1.1-R01 lifts the block. | |
| S1.1-R06 | Death window boundary (§3) | The window is the half-open interval `(t − deathWindowMs, t]`. A death exactly `deathWindowMs` earlier no longer counts; the death at t counts. This is what the S1 code did; v1.1 states it in the spec, and a test pins it. | |
| S1.1-R07 | Auto-farm off (§7, interpretation approved by the owner) | `SetAutoFarm(off)` cancels what auto-farm started: an `auto` walk, an `auto` ordinary encounter, and an automatic wait for a respawn. The enemy is released at full HP, the epoch increments so scheduled events go stale, and regeneration starts. Engagements carry an **origin** (`auto` / `manual`); manual encounters and bosses continue. | In S1, no realistic policy issued `SetAutoFarm(off)` (Rest and Travel already released engagements), so no S1 experiment result depends on this. |
| S1.1-R08 | Regeneration and sessions (§7 audit) | Regeneration starts whenever the hero becomes idle in a session: after a kill with auto-farm off, after a boss timeout, after a cancelled automatic engagement, and at a session start while hurt. A session end also clears a manual `Engage` still waiting for an enemy. Between sessions, world spawn maintenance (`SlotRespawned`) continues; it never changes rewards, EXP, kills, credits or the hero. | These three were real inconsistencies with the written spec (reproductions D7, D8). No S1 experiment reached them: single sessions, and auto-farm always on while farming. |
| S1.1-R09 | Kill-credit identity (§2) | A pending credit is registered at the kill. `KillCredited` is classified **before any draw**: accepted, `CREDIT_REPLAYED`, `CREDIT_CONFLICT` or `CREDIT_UNKNOWN`. A rejected claim changes nothing. An accepted credit is applied with one state assignment, so it is atomic. The committed history is an immutable shared list. If the ledger holds a credit the registry has not committed, that is an engine error. | Normal runs never produce a duplicate, so results are unchanged. The S1 implementation could double EXP and kills, or abort with `TX_CONFLICT` (reproduction D1). |
| S1.1-R10 | Estimator (§5) | Estimator v1.1 (`estimator.md`): an explicit swing budget (100,000 swings, 5,000,000 updates); unresolved mass is never a kill; `null` means "no finite value"; an exact survival chain replaces the renewal approximation. Reliability: **unreachable** / **unsafe** / **approximate** / **reliable**, with reason codes. | The displayed kills per life and rates in dangerous zones change. POL-FRONTIER (kills per life ≥ 10) and POL-BEST-SHOWN (EXP/h) can choose differently; this is reported as a measurement correction. |
| S1.1-R11 | Policy report (§3) | New command `Report(code)` with codes `NO_SAFE_ZONE` and `FIXED_ZONE_BLOCKED`. It changes no game state; it is logged when the shown reason changes. | |
| S1.1-R12 | Drops (§6) | Drops are structured `(resource, quantity, entry)`. Metrics keep successful drop **events** (probability checks, one binomial check per entry) and awarded **quantities** (production rates). Quantities and gold are reconciled with the ledger at the end of every run, and a difference fails the run. | Only `materialsPerHour` could change; S1 content has quantity 1 everywhere, so S1 values are unaffected. |
| S1.1-R13 | Diagnostic controls (§3, §10) | The S1 decision logic is kept as `CTL-STAY-S1`, `CTL-FRONTIER-S1`, `CTL-BEST-SHOWN-S1` and `CTL-FIXED-n-S1` (kind "control"), and the S1 estimator as `estimator: "s1"`. They are used only to reproduce S1 and to attribute changes. The S1.1 runner refuses S1 manifests: their policy names meant the S1 logic, and their results came from the S1 implementation (S1 review package). | |
| S1.1-R14 | Reference farming in diagnostic set-ups (§10) | Estimator-comparison and matched-state audit forks keep the S1 continuous-farming logic (`CTL-FIXED-n-S1`) as their reference, as in S1. The estimator also assumes continuous farming. S1.1-E02 adds `POL-FIXED` cells to show how respecting the stop changes the rates. | Using the corrected fixed policy as the reference would compare the estimate with a run that stops farming after three deaths. |
| S1.1-R15 | Oracle wording (§4) | No oracle is called an upper bound. ORC-BRUTE results are labelled "restricted fixed-zone lookahead (comparison control)". | |
